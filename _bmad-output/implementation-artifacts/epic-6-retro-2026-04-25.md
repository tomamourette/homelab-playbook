## 2. Deep Story Analysis

This section synthesises patterns surfaced from reading every Epic 6 story file
(`6-1` … `6-12` plus the V5 retrospective). Source files cited inline.

### 2.1 Common struggles (issues recurring in ≥2 stories)

**Pattern A — PVE 9 sprint-change pivot (groups → rules model)** appeared in
[`6-3-define-ha-groups.md`](6-3-define-ha-groups.md) and shaped subsequent stories.

The original epic spec (planning-artifacts/pve3-storage-migration-epics.md §"Story 6.3",
lines 974-1008) was written against the legacy PVE 8 HA-groups API. PVE 9.1 deprecated
that API in favour of `ha-manager rules` (node-affinity rules coupled to resource
registration). The first Dev pass on 6-3 (2026-04-24) **correctly stopped at Task 1**
when `ha-manager groupadd` returned "command not supported", rather than improvising —
this is the breakthrough behaviour, not the struggle. The struggle was upstream: the
SM had to re-author the entire story under the rules model on 2026-04-25, absorbing
6-4 (`assign CTs to groups`) into 6-3 because the rules model couples rule creation
and resource registration in a single atomic operation. That cascaded into Story 6.9's
runbook (Failover Scenarios, recovery cookbook all had to be rewritten in PVE 9 idiom)
and into Story 6.10 (alerts query `pve_ha_resource_state` keyed on rule state, not
group state).

**Pattern B — Agent stalls on long-running polls** appeared in
[`6-5-validation-drill-v3-replication-rpo-for-ct162.md`](6-5-validation-drill-v3-replication-rpo-for-ct162.md)
§"Sprint finding" and was the proximate cause of the first 6-5 attempt failure.

The first Dev attempt at 6-5 skipped Task 1 (cadence-tighten ct:162 from `*/15` →
`*/1`) and started AC-3 sampling against the `*/15` schedule that 6-1 had shipped.
With a 15-minute cycle, no `(now - last_sync)` sample was ever going to land under
60 seconds; the sampler ran for ~14 min and the agent stalled when metrics did not
improve. The second attempt explicitly bounded every poll loop:

  - RPO sampler: `for i in $(seq 1 90); do … sleep 10; done` with `timeout 10` on the
    inner SSH; max wall-clock 900 s.
  - Snapshot polls: `for i in $(seq 1 18); do … sleep 5; done`; 90 s ceiling.
  - 15-min sampler: `nohup` background with PID-tracked completion via bounded
    `kill -0 $PID` retries.

The same pattern manifested in
[`6-1-1-add-ct151-replication-jobs.md`](6-1-1-add-ct151-replication-jobs.md) only
because the operator drove the inline V5 recovery in real time alongside Claude —
the recovery sequence (disable → mv config → start) was operator-paced, not
agent-paced, and never stalled.

**Pattern C — Cluster state vs config drift** appeared in
[`6-7-validation-drill-v5-pull-plug-pve3.md`](6-7-validation-drill-v5-pull-plug-pve3.md)
(ct:151 in `standard` HA rule but no replication jobs) and
[`6-9-1-drill-safety-preconditions.md`](6-9-1-drill-safety-preconditions.md) (the
cure: a coverage-audit gate that refuses the drill if any non-pinned HA resource has
fewer than 2 peer replicas). The V5 drill exposed that
`/etc/pve/ha/rules.cfg` (HA placement intent) and `/etc/pve/replication.cfg`
(replication coverage) had no automated cross-check. Story 7-13 (PVE-HA-rules
reconcile mode, backlog) is the deeper version of the same pattern: the
`pve-ha-rules` Ansible role checks resource/rule existence but does NOT reconcile
field drift on `nodes/strict/comment/resources/state/max_relocate`.

**Pattern D — Metric-name typos cascading into wrong claims** is the single
loudest lesson of the epic. The V5 drill reported a "missing `PVEReplicationFailed`
alert" as a critical finding (see
[`v5-drill-retrospective-2026-04-25.md`](v5-drill-retrospective-2026-04-25.md) Gap 2
in original draft, then "Correction note" added 2026-04-25 post-Story-6-10-2). Story
6.10.2 verification showed the drill agent had queried `pve_replication_failcount`
(no underscore) instead of the actually-published `pve_replication_fail_count`
(underscore). The real metric had 10 series — one per job — and the
`PVEReplicationFailing` rule (Story 6.2, `for: 10m`, `severity: critical`) was active
the whole drill. The "exporter gap" finding was wholly fictional. This typo
propagated into Story 6.9's first runbook synthesis as a "broken alert chain"
claim — fix-apply F2 retracted it in five places. Story 6.10.2 was closed as
Branch A (verify-only, no code changes) once the typo was identified.

### 2.2 Recurring review feedback patterns

The BMad cycle for every main-path story was: **SM draft → Dev → Code Review →
Adversarial Review → Fix-apply → flip to done**. Reading the fix-apply notes and
adversarial-review outputs across all 10 main-path stories surfaces five recurring
review themes.

**Theme 1 — Label-mutation gotchas in PromQL.** Surfaced in
[`6-6-validation-drill-v4-simulated-failover-via-migrate.md`](6-6-validation-drill-v4-simulated-failover-via-migrate.md)
adversarial R3 and code review L2. The `pve_ha_resource_state` series mutates its
`exported_node` label on migrate; `changes()` returned 0 during the V4 drill because
`changes()` operates on values within a single time series, but a home-node
transition surfaces as new series creation / old series removal. The honest
verification is `count by (exported_node) (count_over_time(...[20m]))`. A
follow-up story 6-10-3 ("alert rules label-mutation audit") was drafted to
sweep all alert rules for `changes()/rate()/increase()` over label-mutating
series.

**Theme 2 — Runbook synthesis dispersion.** Story 6-9's first synthesis pass
was triaged REQUEST-CHANGES (2 HIGH, 2 MED) by code review and
SHIPPABLE-WITH-FIXES (3 HIGH, 3 MED, 3 LOW) by adversarial review. The runbook
grew 197 → 1115 lines through fix-apply F1–F12, including F2's 5-place retraction
of the typo'd alert-gap claim, F3's PBS topology circular-dependency warning for
Scenario C, F7's prescriptive `mv` cookbook sequence, and F11's vm:100 defensive-
replication rationale. Lesson: a synthesis story over multi-drill evidence
benefits from explicit cross-reference auditing; otherwise small inaccuracies
compound.

**Theme 3 — AC-vacuous-true / AC-N/A handling.** V5 drill (Story 6-7) had
**AC-9 verdict "VACUOUS FAILED"**: the HA fence + relocate completed at T+70 s
(under the 120 s target — fence SLO GREEN), but `pct start` failed at T+159 s
with `dataset does not exist` because ct:151 had no replica. The drill author
correctly distinguished "fence semantic passed" from "application RTO failed
because the prerequisite was incomplete". The story file documents the
distinction with care — but the V5 retrospective then carried the finding
forward as a near-data-loss event, which is the right framing operationally
even if the AC was technically vacuous. Story 6-9-1 (drill safety preconditions)
codified the lesson into Gate 7: **strictly non-overridable** replication-coverage
audit refuses the drill on deficient resources, regardless of `--force --reason`.

**Theme 4 — Operator-confirmation flag handling.** SM Agent A consistently
flagged `[NEEDS OPERATOR CONFIRMATION]` inline rather than guessing. Examples:
6-9 references `architecture.md` path with NEEDS_CONFIRMATION (resolved during
fix-apply); 6-12 (PBS topology) has 3 inline flags (PBS dataset size, pve1 storage
path, current usage); 7-13 has 1 (state-managed-by-operator default for project
CTs). This was a real productivity multiplier — agents that flagged and continued
were strictly better than agents that paused for human input on every uncertainty.

**Theme 5 — Metric/file-name pedantry.** Beyond the V5 typo, the epic surfaced:
the U+2014 em-dash vs ASCII `--` cron file (Story 6-10 first Ansible run; cosmetic);
the `proxmox_hosts` vs `pve_nodes` Ansible-group-name discrepancy (6-10 deviation,
no-op); the `pve_ha_state_exporter_*` vs `pve_ha_exporter_*` metric naming
(6-9-1 corrected to match what 6-10 actually shipped). All low-severity individually,
but collectively a reminder that names matter and `grep` is cheap.

### 2.3 Breakthrough moments

**1. SM Agent A flagged operator-confirmation rather than guessing.** Across
6-3, 6-9, 6-12, 7-13 every uncertain field carried an inline `[NEEDS OPERATOR
CONFIRMATION]` flag with the specific question. No agent invented Authelia paths,
PBS dataset sizes, or storage classes. This is a hard skill to teach; it surfaced
naturally in this epic.

**2. Dev Agent on 6-3 stopped at Task 1 instead of improvising** when
`ha-manager groupadd` returned "command not supported" on PVE 9.1. A weaker
response would have been to invent a `pvesh /cluster/ha/groups` POST sequence;
instead the Dev halted, the SM ran sprint-change to author the rules-model
rewrite, and the second Dev pass executed cleanly. **This saved cluster state.**

**3. Inline V6 recovery driven by operator + Claude live.** When V5 left ct:151
in error state on pve1 (no replica), the recovery sequence (`ha-manager set
ct:151 --state disabled` → `mv /etc/pve/nodes/pve1/lxc/151.conf
/etc/pve/nodes/pve2/lxc/151.conf` → `--state started`) was driven in real time:
operator on the cluster, Claude reading state and proposing each step. Heartbeat
came through byte-identical. This was where the BMad pair model showed its
value most clearly.

**4. ct:151 replication gap caught BY the drill.** No alert, no monitoring
dashboard, no health check, and no prior story had surfaced ct:151's missing
replication. The cluster reported itself healthy; a real pve2 failure would have
been a data-loss event recoverable only via PBS restore. The V5 drill paid for
itself in a single execution. This is the canonical justification for chaos
drills.

**5. SM Agent on 6-3 absorbed Story 6-4 into 6-3** when the rules model coupled
rule creation and resource registration. A weaker SM would have created a
"6-3-revised" and left 6-4 dangling; the actual SM marked 6-4 `superseded` with
the original AC matrix archived in the file body for historical reference. Clean
move.

### 2.4 Velocity patterns: how the BMad cycle shaped quality vs cost

The cycle SM → Dev → Code Review → Adversarial Review → Fix-apply → done was
applied to every main-path story. Concrete observations:

- **Multi-agent parallelism was a real productivity multiplier.** SM A drafted
  6-9 while SM B drafted 6-9-1, 6-12, 7-13 in parallel. Code Review and
  Adversarial Review on 6-9 ran in parallel on different LLM contexts. The
  fix-apply for 6-9 then took both review outputs as input, which
  produced 12 distinct findings (3 HIGH + 3 MED + 6 LOW from review; 3 HIGH +
  3 MED + 3 LOW from adversarial) that converged on a single fix-apply pass.

- **The Adversarial Review consistently found things Code Review missed.**
  Specifically: V5 retro typo'd alert-claim (caught in 6-9 adversarial, F2
  retraction); PBS single-host circular dependency (caught in 6-9 adversarial
  R2 → spawned 6-12); cron-daemon-death observability gap (caught in 6-10
  adversarial R3 → spawned 6-11); `ha-manager set --state stopped` rejected
  on resource-already-in-error (caught in 6-10 review M1+R5 → memory captured
  in `feedback_pve9_ha_error_recovery.md`).

- **Fix-apply usually triaged 60-80% of findings to follow-up backlog.** Story
  6-9's 12 findings split: 11 fix-applied in-place (F1–F12), 1 spawned new
  story (6-12 PBS topology). Story 6-10's many findings split: M1+R5+M2+M3+R12
  +R13+R9 fix-applied; R1+R8 → 6-10-1; R3 → 6-11; R7 → 6-9-1. **The fix-apply
  triage pattern is healthy: don't try to do everything in one story; spawn
  focused follow-ups.**

- **Cycle cost was non-trivial but bounded.** Each main-path story consumed
  on the order of 4–8 agent invocations (SM × 1 + Dev × 1 + Code Review × 1
  + Adversarial × 1 + Fix-apply × 1, sometimes with a second Dev pass).
  Total agent time across Epic 6 main path: substantial but every
  invocation produced reviewable artefacts.

### 2.5 Team collaboration highlights

The **planner + coder + reviewer + analyst quartet pattern** stabilised across
the epic. Specifically:

- **planner** (SM) drafted stories with explicit AC, Tasks, Dev Notes, Test
  strategy, Rollback procedure, References sections. The template held under
  pressure.
- **coder** (Dev / Amelia) executed tasks, captured evidence files, recorded
  AC verdicts in a fixed table format, listed deviations explicitly, and
  always flipped status `draft → review` (never to `done`).
- **reviewer** (Code Review) triaged findings into HIGH/MED/LOW and produced
  a verdict (APPROVE / APPROVE-WITH-MINOR / REQUEST-CHANGES / BLOCK-ON-FIX).
- **analyst** (Adversarial Review) assumed the role of cynical reader and
  surfaced things Code Review missed, with HIGH findings often spawning
  follow-up stories.

The hand-offs between these four were file-based (story file + evidence dir)
not chat-based, which made them resumable across context windows.

## 4. Challenges

1. **PVE 9 sprint-change pivot mid-sprint (HA groups deprecated → rules model).**
   Story 6-3 had to be rewritten root-to-tip; Story 6-4 was absorbed into 6-3;
   Stories 6-9, 6-10 had to be authored against the new model. This consumed
   real cycle time but produced a clean PVE-9-native result. (See
   `6-3-define-ha-groups.md` §"Sprint change note", lines 17-20.)

2. **V5 drill exposed a real ct:151 replication gap**, causing a 30-min
   stranded recovery window. The drill caught it (which is the canonical
   justification for chaos drills), but the alternative — discovering it on a
   real pve2 failure — would have been a data-loss-class incident. Story
   6-1-1 closed the gap with two new replication jobs (151-0 → pve1, 151-1 →
   pve3) and codified all 10 jobs into the new `pve-ha-replication` Ansible
   role.

3. **Multiple "agent stalled on long-running poll" incidents.** First Dev
   attempt at Story 6-5 stalled when sampling a `*/15` cycle for 1-min RPO
   (no sample was ever going to hit < 60 s). First Dev attempt at Story 6-3
   stalled on a deprecated API. Both incidents required human takeover —
   the operator stopped the agent, the SM authored the fix, the second Dev
   pass succeeded. **This is a known limitation of agent execution: poll
   loops without convergence criteria stall indefinitely.** The 6-5 second-
   attempt explicitly bounded every poll loop with `for i in $(seq …)`
   counters and `timeout` per inner SSH; that pattern is now mandatory.

4. **Metric-name typo (`pve_replication_failcount` vs `pve_replication_fail_count`)
   caused a cascade of wrong claims** in the V5 drill retrospective and Story
   6-9 synthesis. The retraction took 5 in-place fixes (F2 in Story 6-9
   fix-apply) plus a "Correction note" appended to the V5 retro doc plus
   closing 6-10-2 as Branch A (verify-only). **Lesson**: cross-check metric
   names against exporter source before declaring a "missing metric" finding.
   `grep -E '^pve_replication_' /var/lib/prometheus/node-exporter/pve_replication.prom`
   would have caught this in seconds.

5. **Sprint-status YAML uses non-BMad statuses.** The file has
   `done-with-finding`, `done-with-recovery-inline`, `done-partial`,
   `superseded`, `partially-done`, `done-with-exception`,
   `done-with-tfstate-drift`, `done-with-scope-change`, `done-with-scope-revisions`,
   `done-pending-scrub`, `blocked-on-operator`, `done-soft`. The retrospective
   workflow vocabulary (`backlog`/`ready-for-dev`/`in-progress`/`review`/
   `done`/`optional`) diverges. This is acceptable for this multi-project
   repo (the homelab sprint legitimately needs richer state markers for
   audit) but means automated consumers of sprint-status must understand
   the extended vocabulary.

6. **Backlog accretion**: 11+ follow-up stories drafted but not implemented.
   This is **healthy fix-apply triage** (don't try to do everything in one
   story; spawn focused follow-ups), but it does mean post-Epic-6 the
   backlog has more drafted items than implemented items. Most are
   nice-to-haves and operator-decisions; none block production-readiness.

## 5. Lessons Learned

The 8 OMEGA memories already capture the principal lessons (no new memory writes
needed in this retro). Brief restatement for the record:

1. **Vault-backed secrets flow** (`project_ai_dev_container.md` and Story 7.11
   close-out): vault-backed Cloudflare token via `playbooks/sync-cloudflare-token.yml`
   is the canonical pattern for secret rotation. `docker compose restart` does
   NOT re-read `.env`; use `up -d --force-recreate`.
2. **PVE 9 HA model** (`project_pve9_ha_rules_migration.md`): groups are
   deprecated; node-affinity rules couple rule creation and resource registration;
   `failback` is per-resource (replaces legacy group-level `nofailback`). PVE 9
   refuses `ha-manager set --state stopped` on a resource already in `error` —
   the recovery path is `disabled` → fix root cause → `started`.
3. **Project-CT HA state policy** (per Story 6-3 implementation): always-on
   infrastructure CTs (101/162) get `--state started`; project CTs (151/250)
   get `--state started` IF currently running, else `--state stopped`. Operator
   can over-ride per-resource.
4. **YAML block-scalar trap** (per Story 6-3 fix-apply): `>-` block scalars
   preserve `\\s` as literal two-character `\\s`; inline double-quoted strings
   correctly escape `\\s` → `\s`. Use inline strings for regex patterns in
   Ansible.
5. **PVE 9 HA error recovery** (`feedback_pve9_ha_error_recovery.md`): full
   recovery sequence captured for the case where a resource ends up in
   `error` with no replica on the chosen failover target.
6. **Tailscale notifications** (Story 7.11): ntfy-urgent topic, send_resolved=true,
   group_wait=10s, repeat_interval=4h, case-insensitive severity matcher.
   `homelab-alerts-urgent` topic verified end-to-end on operator phone.
7. **Audit-first principle** (`feedback_ha_replication_audit_first.md`): before
   any HA-related work, audit replication coverage versus HA rule placement.
   Codified into Story 6-9-1 Gate 7 (strictly non-overridable).
8. **Hybrid-gemma research** (separate planning artefact): not directly Epic 6
   but adjacent; AI-services-on-pve3 architecture is documented and ready for
   future epic.
