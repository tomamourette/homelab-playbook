## Challenges and Growth Areas

### Pattern 1: Error Handling Gaps (4/5 stories)

| Story | Finding |
|-------|---------|
| 0.1 | No error handling for create-story failure |
| 0.3 | No git availability check |
| 0.4 | Heading not found in doc — no fallback |
| 0.5 | No failure handling for delegated bmad-document-project |

**Root cause:** Story template doesn't prompt for error scenarios. Happy path is built first, error cases caught only at review.

### Pattern 2: Repeated Deferrals (mode detection keyword ambiguity)

Deferred in Stories 0.3, 0.4, and 0.5 — each time marked "pre-existing." Three reviews discussed the same item.

**Root cause:** No rule preventing indefinite deferral. Repeated discussion costs more than fixing.

### Pattern 3: Ambiguous Boundaries (read-only vs state tracking)

Check mode was incorrectly writing `git_ref_at_last_update` (advancing the baseline) when it should only record observational state. PRD said "read-only" (FR47) but also "track state" (FR50). Architecture resolved the tension but the boundary between "observing" and "advancing" wasn't explicit.

**Root cause:** Requirements used terms ("read-only", "state tracking") without defining permitted side effects.

### Pattern 4: Unbounded Input Size

Story 0.4 deferred W2: source file contents stuffed into LLM context could overflow with many changed files.

### Pattern 5: Cross-Session Testing Limitation

Skills can't be tested in the session that creates them. Story 0.1 deferred Task 5 (wrapper test). Story 0.3 noted the same constraint.

## Key Insights and Learnings

1. **Eval assertions and autoresearch are implementation quality tools, not skill-improvement tools.** They work for Ansible roles, scripts, and any code — not just Claude Code skills. The eval-review-fix loop is domain-agnostic.

2. **The wrapper skill pattern is the interface to BMAD.** We use wrappers, extend them, but never reach past them into bmad-* files. `/create-story-with-evals`, `/code-review-ab`, `/update-project-docs` — all wrappers.

3. **A deferral that repeats across stories isn't a deferral — it's accepted technical debt.** It accumulates review overhead and should be promoted to a backlog item or fixed.

4. **When a requirement uses terms like "read-only," the architecture step should explicitly define what side effects are permitted.** A one-line "Side Effects" row in the decision table prevents ambiguity.

5. **In-flight scoping discipline works:** surface the idea, assess scope and impact, then patch (if small), defer with documentation (if architectural), or correct course (if epic-changing).
