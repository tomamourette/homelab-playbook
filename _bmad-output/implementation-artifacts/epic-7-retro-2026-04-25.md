# Epic 7: Reproducibility & Guardrails — Retrospective

## 1. Epic 7 Summary

Epic 7 is the codification capstone of the pve3-storage-migration program: every
architectural lesson learned in Epics 1–6 is now captured as code, CI guardrail,
runbook, or memory file. The original incident pattern (HA CT on non-replicable
storage) is now mechanically prevented at commit time. The 2-hour Window B
manual cluster recovery is now a single Ansible playbook. The pve3 Option D
storage layout is reproducible from a clean install. Push alerts to the
operator's phone replace polling-only monitoring.

Epic 7 was authored **in parallel with Epics 1–6** per the workflow design note
in `pve3-storage-migration-epics.md` line 191: "Epic 7 work (Ansible role
authoring, CI guardrail) can be developed in parallel with earlier epics; its
delivery is gated on all prior epics being complete so the codified artifacts
reflect reality." This worked beautifully and produced a notable side effect:
Epic 7 **grew during the sprint** from 7 stories at planning time to 14 stories
by closure — the additions (7-8 through 7-14) were stories born from lessons
learned in real time, captured into Epic 7 rather than becoming orphan
hardening tickets.

## 2. Deep Story Analysis

This section synthesises patterns across all Epic 7 story files (`7-1` … `7-13`,
plus contextual references to 7-7/7-8/7-10/7-12/7-14 from sprint-status entries
since those don't have standalone story files).

### 2.1 Common struggles (issues recurring in ≥2 stories)

**Pattern A — Ansible idempotency in PVE-land has sharp edges.** Surfaced in
[`7-1-author-ansible-role-pve-host-pve3-storage.md`](7-1-author-ansible-role-pve-host-pve3-storage.md)
(post-adversarial Fix 5: `awk '/^\s*special$/'` regex missed newer ZFS status
output where the `special` section header carries trailing status text), in
[`7-2-idempotency-test-of-ansible-role-against-fresh-state.md`](7-2-idempotency-test-of-ansible-role-against-fresh-state.md)
(`community.general.zfs` check-mode false-positives — module cannot introspect
existing properties so reports `changed=3` even when state matches), in
[`7-9-ansible-pve-node-bootstrap-playbook.md`](7-9-ansible-pve-node-bootstrap-playbook.md)
(known_hosts alias-keying mismatch guaranteed non-idempotency on re-runs;
fixed by keying each entry on `line.split()[0]` and scanning each alias
separately), and in [`7-13-pve-ha-rules-reconcile-mode.md`](7-13-pve-ha-rules-reconcile-mode.md)
(presence-checks vs field-drift reconciliation — the deeper version of the
same axis). The recurring lesson: **PVE's CLI tools and ZFS modules don't
play perfectly with Ansible's idempotency contract.** Workarounds that worked:
slurp + regex_findall instead of `lineinfile`/`blockinfile` for content the
module can't safely round-trip; probe-before-act with `zpool list -H`,
`zdb -C`, `pvesh get`; explicit hostname guards; `from-iso` not inline for
answer.toml (PVE 9.1.7 limitation).

**Pattern B — Cluster-wide vs single-node delegation race conditions.**
Story 7-9 had to handle SSH trust setup in **both directions** (target → peers
AND peers → target) with peers-might-be-offline fault tolerance. The first
implementation had a `known_hosts` alias-key mismatch that was guaranteed
non-idempotent (H-1, H-2 in code review). The fix: scan each alias separately
(IP, FQDN, short hostname), key each entry on `line.split()[0]`, fall back
from `ansible_facts['default_ipv4']` to canonical IP from `cluster_members`
when facts aren't available. Story 6-3 (Epic 6) hit a related pattern in the
`pve-ha-rules` role — `ha-manager rules add` needs to run on exactly one
cluster node but the role applies to all three; the solution was `run_once`
+ `delegate_to`. Both stories taught the same operational lesson: **cluster
config writes need exactly one writer, but cluster config reads need all
peers to be reachable.**

**Pattern C — PVE 9.1.7 deprecated features not in install-time tooling.**
Story 7-9 R1 (catastrophic blocker) discovered that `proxmox-auto-install-
assistant 9.1.7` does NOT support `[first-boot] source = "inline"` despite
documentation saying otherwise — only `from-url` and `from-iso` are accepted.
The fix: use `from-iso` with companion `pve3-firstboot.sh` baked into the
ISO via `proxmox-auto-install-assistant prepare-iso --on-first-boot`. This
was the same flavour of issue as Epic 6's PVE 9 HA-groups deprecation:
**docs lag the binary**, and the only safe path is to validate against the
actual installed CLI version with `validate-answer` or equivalent. The
adversarial review caught it; the planner had assumed inline would work
because the wiki said so.

**Pattern D — Alertmanager `webhook_configs` API expressiveness limit.**
Story 7-11 hit a real limit of Alertmanager's webhook receiver: a single
receiver can POST one body shape to one URL, so mapping three Prometheus
severity levels (critical/warning/info) to three different ntfy priorities
(urgent/default/low) required **3 separate ntfy topics** and **3 separate
receivers**, not one receiver with header-based priority. The Option C
solution (3 topics: `homelab-alerts-urgent`, `homelab-alerts-default`,
`homelab-alerts-low`; 3 webhook receivers; 3 routes by severity matcher) is
documented in the story file. The phone subscribes to all three with
different DND-bypass settings. **Lesson**: Alertmanager treats severity as a
routing label, not a payload field; design accordingly.

**Pattern E — Story scope absorption from adversarial reviews.** Story 7-13
absorbs Story 6-3 adversarial-review finding R3 (MEDIUM): "the `pve-ha-rules`
role only checks resource/rule existence, does NOT reconcile field drift in
nodes/strict/comment/resources/state/max_relocate". Story 7-12 (vault
rendering) absorbs the Story 7-11 R3 finding about scattered Cloudflare token
storage. Story 7-14 absorbs the 6-9-1 fix-apply F5 deviation about the
ct-dev-homelab inventory drift. **Pattern: when fix-apply triages a
finding to a follow-up story, that story usually lands in Epic 7 because
Epic 7 IS the codification dumping ground.** This is a feature, not a bug.

### 2.2 Recurring review feedback patterns

**Theme 1 — Ansible task names are hyphenated lowercase project precedent.**
Story 7-9's first lint pass had 27× `name[casing]` violations because task
names started with lowercase tag prefixes like `"hosts | …"`. The project
convention surfaced via lint feedback: capitalise the tag prefix, e.g.
`"Hosts | …"`, `"NIC | …"`, `"SSH | …"`, `"Cluster-join | …"`,
`"Validate | …"`. This convention is now baked into all Epic 7 + Epic 6
roles. A follow-up Epic could codify this as a `.ansible-lint` config
addition.

**Theme 2 — Idempotency guards using slurp + regex_findall (not lineinfile).**
Story 7-1 originally used `blockinfile` with named markers for `/etc/exports`
edits; the pattern works but shows up as `changed=1` on reruns when the file
has any unrelated edits. Story 6-1 / 6-1-1 / 6-3 / 7-9 evolved a stricter
pattern: `slurp` the file content into Ansible memory, parse with
`regex_findall`/`regex_search`, compute the diff against desired state, and
ONLY emit `command` tasks for the genuinely-divergent fields. The
`pve-ha-replication` role (Story 6-1-1) and the `failback.yml` task in
`pve-ha-rules` (Story 6-3 Task 3) are canonical examples. Story 7-13's whole
purpose is to extend this pattern to all rule + resource fields.

**Theme 3 — Per-resource-state vs presence-only role design.** Story 7-1
explicitly chose presence-only design for safety: "the role does not
implement `zpool destroy`, dataset removal, or `/etc/exports` entry removal.
That's on purpose, but it means 'drift from the authored state' won't be
reconciled." Story 7-13 is the bookend: presence is sometimes not enough.
The right rule is **presence-only for destructive paths** (don't destroy
operator data) **plus reconcile-mode for additive/mutative fields** (don't
let operator-edits silently persist as policy). This is a non-trivial design
axis and Epic 7 surfaced it explicitly.

**Theme 4 — SHA-parity invariants for canonical-script + role-copy.** Story
6-9-1 fix-apply F6 added a SHA-drift check between the canonical
`drill-safety-preflight.sh` script and the copy in
`drill-safety/files/drill-safety-preflight.sh`. The pattern is operationally
important: Ansible roles ship file copies that can drift from the canonical
upstream version. Future Epic 7-style codification should establish a
standard for "single source of truth + SHA-verified Ansible role copy" so
the role can detect drift and refuse to converge until the copy is
refreshed. This pattern is **not yet codified into a memory** but should be.

**Theme 5 — Deferred "real" runs with explicit rationale.** Story 7-1
deliberately deferred dry-run + fresh-state validation to Story 7-2 ("its
whole point is clean-slate-rebuild proof"). Story 7-9 dev-agent prompt
forbade running against production, so the `--check --diff` against pve2
was deferred to the operator. Story 7-3 deliberately did NOT wire cron on
pve2 / install pre-commit hook / push status file — "operator will review
adversarially before activation". This **explicit-deferral discipline** is
healthy: each story has a tight scope, the next-step is documented, and
nothing is silently dropped.

### 2.3 Breakthrough moments

**1. Story 7-9 `pve-node-bootstrap` automated 2-hour Window B manual
recovery into a single playbook run.** This is the single highest-impact
deliverable in Epic 7. Window B (pve2 reinstall on 2026-04-24) consumed
~2 hours of hand-editing `/etc/hosts`, `/etc/network/interfaces`, manual
SSH-key distribution, and a `pvecm add` retry due to split-brain state. The
Story 7-9 playbook captures **all six** Window B gotchas (stale `/etc/hosts`,
DHCP-pinned wrong NIC, dangling `authorized_keys` symlink, NIC interface
naming shifts, `pvecm add --use_ssh` requiring bidirectional trust,
WAN-port confusion) into idempotent task blocks. **Idempotency proven** on
pve2: 11 changed → 1 → 0 over three consecutive runs; `--check --diff` is
clean. Future pve3 reinstalls are a single playbook invocation with no
manual steps beyond physical-keyboard ISO boot.

**2. Story 7-3 CI guardrail prevents the original-incident pattern from
ever silently re-emerging.** The script reads the **authoritative**
`/etc/pve/ha/resources.cfg` (post-adversarial fix in Fix 1, which closed the
GUI-bypass case where `/etc/pve` was added without per-VMID tagging). Eight
fixtures cover the bypass, multi-mount partial-bad, VM-with-bad-disk,
unknown-storage warning paths. The blocklist is regex+whitelist hybrid
rather than 4-element exact-match (so `fast-pool-staging` won't accidentally
pass). The status-file flow has `STRICT_AFTER_DATE` so PRs are warned during
roll-out and hard-failed afterwards. **No future operator can commit a
"shared-nfs-bulk:vm-disk-0.raw" line on an HA-tagged CT and pass CI.**

**3. Story 7-11 vault-backed Cloudflare token flow is the canonical pattern
for secret rotation.** The token now lives in
`vault_cloudflare_api_token` (Ansible Vault), is materialised to
`terraform.tfvars` and CT101 `.env` by `playbooks/sync-cloudflare-token.yml`,
and is rotated by editing the vault file once + re-running the playbook.
This pattern is **proven mechanical extension** to other secrets:
`pve_token_secret`, `PORTAINER_AGENT_SECRET`, `TRAEFIK_ADMIN_PASSWORD_HASH`,
`dev_vm_password`, Authelia secrets. Story 7-12 documents that the
extension is deferred until each secret needs rotation or a new consumer —
the right deferral, because rotating-just-because is operationally
expensive and cosmetic.

**4. Story 7-1 post-adversarial 10-fix pass produced a hardened role with
zero behaviour change on the production pve3 target.** All 10 fixes
(hostname guard, ZFS module precheck, exported/FAULTED pool handling,
cluster-join precheck for nfs-export, special-vdev probe regex, PBS task
ordering, hardcoded NFS server IP, handler noise, test playbook scope,
collection requirements documentation) were additive or refactoring — none
removed existing idempotency. The role lints clean at production profile
and runs `changed=0` on real reconciled pve3.

**5. Story 7-8 fixed the DHCP-pin foundation that made Story 7-9 possible.**
Without 7-8 (DHCP reservations on Asus router for pve1/pve2/pve3 MACs →
.201/.202/.203), Story 7-9 would still have been needed but would have
additionally had to **discover** the freshly-installed node's IP at runtime.
With 7-8 the playbook can hardcode the canonical IPs in `cluster_members`
and trust the network. **This is a clean dependency chain:** 7-8 (DHCP) →
7-9 (bootstrap) → Epic 3 Story 3.3 (cluster rejoin) → Epic 6 (HA
activation). 7-8 took ~30 minutes of NVRAM editing on the router; the cost
ratio of "30 min of DHCP work to enable 2-hour saving per future reinstall"
is excellent.

### 2.4 Velocity patterns: parallel authorship paid off

The workflow design note "Epic 7 codification work may be AUTHORED in
parallel" was applied aggressively. Concrete observations:

- **Stories 7-1, 7-3, 7-4, 7-6 were authored well before Epic 6 was
  thinkable.** They captured the "this is what the cluster should look like
  in Ansible/Terraform/CI" intent at planning time and were validated
  against the actually-built cluster only after Epics 1–5 closed.

- **Stories 7-8, 7-9, 7-10, 7-11, 7-12 were AUTHORED MID-SPRINT.** They
  emerged from real gaps: 7-8 from the Window B DHCP failure mode, 7-9 from
  the Window B 2-hour recovery, 7-10 from a pve3 BIOS planning gap, 7-11
  from the Story 6-2 adversarial-review finding that monitoring was
  polling-only, 7-12 from the Story 7-11 R3 about scattered token storage.
  Epic 7 GREW from 7 stories to 14 during the sprint. **This is a healthy
  growth pattern**, not a planning failure: the original 7 stories captured
  the "obvious" codification, and the additions captured the
  "discovered-during-execution" codification.

- **Stories 7-13, 7-14 were authored as backlog drafts** — captured at
  triage time but explicitly deferred. Both are small (358-line story for a
  field-drift reconcile pattern; 5-line inventory fix). Neither blocks
  Epic 7 or sprint closure.

- **Story 7-9 was the single most expensive story in Epic 7**: 8 High +
  14 Medium + 22 Low code-review findings + 15 adversarial findings (2
  catastrophic). All resolved over a single review-fix pass. Idempotency
  proven via 3 consecutive runs on pve2 (`changed=11 → 1 → 0`).
  **Heavy review pays off** when the deliverable is a multi-host
  cluster-join playbook with bidirectional SSH trust and a
  catastrophic-blast-radius (cluster-state corruption) failure mode.

Story 7-9 is the model for "high-stakes infrastructure" stories in this
sprint:

- **Dev** (Amelia / Claude Opus 4.7) executed the 10 tasks, captured

The hand-offs across SM → Dev → Code Review → Adversarial Review →

## 4. Challenges

1. **PVE 9 deprecated HA groups mid-sprint** (Epic 6 caught it but Epic 7's
   `pve-ha-rules` role had to be authored against the new model). This is
   captured in the Epic 6 retro §4 challenge 1; from Epic 7's perspective
   the impact was: the `pve-ha-rules` role authored in Story 6-3
   absorbed Story 6-4 ("assign CTs to HA groups") because the rules model
   couples rule + resources at creation. Story 7-13's reconcile-mode
   draft accommodates the new model.

2. **`community.general.zfs` check-mode false positives.** The module
   cannot introspect existing ZFS property values in `--check` mode and
   reports `changed` for every property task even when state matches
   desired (Story 7-2 Run 4: `changed=3` in check mode against an
   already-reconciled pve3). This is documented and acceptable but means
   `--check --diff` runs against ZFS-property-heavy roles always show
   noise that operators must learn to ignore. **Lesson**: real-mode
   idempotency is the test, check-mode is a guideline.

3. **PVE 9.1.7 doesn't support inline answer.toml.** Story 7-9 R1
   catastrophic blocker: `proxmox-auto-install-assistant 9.1.7` rejects
   `[first-boot] source = "inline"`, only `from-url` and `from-iso` are
   accepted. The fix was switching to `from-iso` with companion
   `pve3-firstboot.sh` baked into the ISO via
   `proxmox-auto-install-assistant prepare-iso --on-first-boot`. Validated
   via `validate-answer` on the actual pve3 binary. **Lesson**: docs lag
   the binary; always validate against the actual installed CLI version.

4. **PBS apt task hits `pbs-enterprise 401` on first run.** Story 7-2
   Run 1 failed at `Install proxmox-backup-server` because
   `update_cache: true` refreshed all configured apt sources including
   `/etc/apt/sources.list.d/pbs-enterprise.sources` which requires a paid
   subscription. PBS is already installed and the datastore registered;
   the failure is cosmetic. Documented as done-with-finding; the
   proposed fix (precheck `dpkg -l proxmox-backup-server` before
   `update_cache`) is captured in the Story 7-2 Dev Agent Record but
   deferred — no urgency since PBS doesn't need re-install in production.

5. **Vault auto-load doesn't work in this Ansible setup.** Project
   convention discovered late: playbooks must explicitly
   `vars_files: vault.yml` rather than relying on automatic loading from
   `inventories/*/group_vars/vault.yml`. Story 7-11 hit this when
   `sync-cloudflare-token.yml` couldn't see `vault_cloudflare_api_token`
   until the explicit vars_files line was added. **Lesson worth
   capturing as a memory** (see §5 for proposed new memory).

6. **Alertmanager `webhook_configs` API limit** required Option C
   (3-topic ntfy split) instead of header-based priority. This is a
   real Alertmanager limitation, not a project mistake, but it added
   complexity to the Story 7-11 deployment: 3 topics, 3 receivers, 3
   routes, phone subscribes to all three with different DND-bypass
   settings.

7. **Story 7-13 absorbed scope from 6-3 adversarial review** (deferred
   field-drift reconciliation). The Epic 7 backlog has 1 substantive item

## 5. Lessons Learned

The 9 OMEGA memories already capture the principal sprint-wide lessons
(no new memory writes strictly needed in this retro). Brief restatement
plus 3 new lessons emerging from Epic 7 specifically:

### Already captured in OMEGA

1. **PVE 9 HA migration** (`project_pve9_ha_rules_migration.md`):
   groups deprecated; node-affinity rules couple rule + resource
   creation; per-resource `failback` replaces legacy group-level
   `nofailback`.

2. **Project-CT HA policy** (`project_project_container_ha_policy.md`):
   project CTs (151/250) get `--state started` if running,
   `--state stopped` if not; always-on infra (101/162) always
   `--state started`.

3. **YAML block-scalar regex trap** (`feedback_yaml_block_scalar_regex.md`):
   `>-` block scalars preserve `\\s` literally; use inline double-
   quoted strings for regex patterns in Ansible.

4. **PVE 9 HA error recovery** (`feedback_pve9_ha_error_recovery.md`):
   recovery sequence for resource-in-error-state with no replica:
   `disabled` → fix root cause → `started`.

5. **Audit-first principle** (`feedback_ha_replication_audit_first.md`):
   before any HA-related work, audit replication coverage versus HA
   rule placement.

6. **Tailscale phone notifications** (`project_phone_notifications_tailscale.md`):
   ntfy-urgent topic, send_resolved=true, group_wait=10s,
   repeat_interval=4h, case-insensitive severity matcher, 3-topic
   split for priority mapping.

### Emerging in Epic 7 — not yet captured but should be

7. **Ansible vault auto-load behaviour in this repo** (NEW —
   recommended new memory `feedback_ansible_vault_explicit_load.md`):
   playbooks must explicitly `vars_files: vault.yml` rather than
   relying on automatic loading from `inventories/*/group_vars/vault.yml`.
   Story 7-11 hit this; without the explicit reference,
   `vault_cloudflare_api_token` is undefined at template-render time
   even with the right inventory. Encode in memory so the next
   secret-rendering story doesn't re-discover it.

8. **CI guardrail vs runtime guardrail distinction** (NEW —
   recommended new memory `feedback_ci_vs_runtime_guardrails.md`):
   Story 7-3 catches violations at commit time (cheap, immediate);
   Story 6-9-1 drill-safety preflight catches violations at runtime
   (expensive, immediately-before-action). Both are valuable; they
   cover different failure modes (commit-time = "operator typed
   wrong storage", runtime = "config drifted since last commit").
   Codify the distinction so future guardrail stories pick the
   right tier.

9. **Role-vs-canonical-script SHA invariants** (NEW — recommended
   new memory `feedback_canonical_script_sha_drift.md`): Story 6-9-1
   F6 added a SHA-drift check between the canonical
   `drill-safety-preflight.sh` script and the copy in
   `drill-safety/files/`. The pattern is operationally important:
   Ansible roles ship file copies that can drift from the canonical
   upstream version. Codify "single source of truth + SHA-verified
   role copy" as the standard for any new
   role-with-bundled-canonical-script.

These three new memories are recommended but not mandatory; they're
operational refinements of patterns the sprint already used implicitly.
Operator can write them at leisure.
