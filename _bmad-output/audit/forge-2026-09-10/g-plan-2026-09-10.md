## 4. The procedure

Ordering principle: **make the pref change observable and reversible before making it permanent.**
The riskiest single action (flipping `RouteAll`) is done first, live, with zero restart, so it can
be watched and undone in one command. The compose change then only *persists* what is already true.

mkdir -p ~/g-backup-$STAMP

## 5. Risks and blast radius

### 5.1 Expired auth key at recreate time — LOW, and mitigable

`feedback_tailscale_auth_recovery.md` is right that the container reports `Up (healthy)` while
logged out: the healthcheck is `tailscale status --json`, which exits 0 in the `NoState` /
logged-out case. That failure mode is real but **is not reachable by this change**:

- `tailscaled.state` (2,746 B, 2026-09-03) is bind-mounted from `/opt/appdata/...`, which
  `docker compose up -d` does not touch. The container restarts into the same state.
- With valid state, the start script takes the `BackendState == "Running"` branch and **never
  reads `TS_AUTHKEY`**.
- `homelab-gateway` has **node-key expiry disabled** (`Self.KeyExpiry: null`), so the session
  cannot lapse on a timer while the container is stopped for those 10 seconds.

**How to check key validity before recreating** — there is no read-only test, so use these proxies:

```bash
# 1. Is the session actually live right now (not just "healthy")?
$SSH 'docker exec tailscale tailscale status' | head -3
#    A logged-out node prints "You are logged out. The last login error was: ..."
$SSH 'docker exec tailscale tailscale status --json' | jq '.BackendState, .Self.Online, .AuthURL'
#    expect "Running", true, ""       <- a non-empty AuthURL means it wants re-auth

# 2. Is the persisted state present and non-trivial?
$SSH 'stat -c "%n %s %y" /opt/appdata/networking-tailscale/tailscale/tailscaled.state'
#    expect ~2.7 KB, not 0

# 3. Key class and rough age (no value printed).
$SSH 'ls -la /opt/homelab-apps/stacks/networking-tailscale/.env*'
#    .env is Jul 28; .env.bak-deadkey is Jul 27 = last rotation. A tskey-auth-* on the
#    90-day default therefore expires ~2026-10-25. INFERRED, not measured.
```

If (1) shows anything other than `Running`/`Online`, **stop** and rotate the key per the memory
file's recovery procedure before touching compose — a recreate would then be the moment the node
falls off the tailnet, and the blip becomes an outage.

### 5.2 Does `docker compose up -d` with `network_mode: host` disturb Pi-hole or Traefik? — NO

- `network_mode: host` means the container shares CT 101's network namespace. It publishes no
  ports and creates no bridge, so it collides with nothing. Traefik (80/443) and Pi-hole (53, 8053)
  are untouched — verified: the tailscale container has no port bindings and no `proxy` network
  attachment.
- Compose scoping is by project. `networking-tailscale` is a separate project from `dns-pihole`
  and `infra-core` (confirmed via container labels and `docker compose config --services`, which
  returns exactly `tailscale`). Running compose from that directory cannot enumerate, stop or
  recreate a container belonging to another project.
- The one real hazard is **operator error**: running `docker compose up -d` from `/opt/homelab-apps`
  or passing `-f` for a different stack. G3 pins both `-f` and `-p` to make that impossible.
- Pi-hole rescue path if anything DNS-shaped goes wrong: `docker restart pihole` (seconds).
  **Never `pihole restartdns`** — it hangs forever on this image and can leave the s6 service down.

### 5.3 Does the blip affect this workbench's or the operator's session? — NO

| Path | Depends on `homelab-gateway`? |
|---|---|
| This workbench (CT 250) → CT 101 over SSH | **No.** `ip route get 192.168.50.194` → `dev eth0`. Plain LAN, same /24. |
| Operator off-LAN → CT 250 | **No.** CT 250 is its own kernel-mode tailnet node (`100.104.114.63`, `tag:control`, `tailscale0` present, `RouteAll: false`). It is reached as a direct peer, not through the subnet router. |
| Operator off-LAN → any LAN host **by LAN IP** (`192.168.50.x`) | **Yes.** ~10 s of loss while the container recreates. This is the only thing that blips. |
| Operator off-LAN → Pi-hole split DNS at `192.168.50.194` | **Yes**, same ~10 s. |
| Public ingress (`hermes.bi-services.be` via Cloudflare Tunnel) | **No.** `cloudflared` is a separate container in the `infra-core` project, egress-only to Cloudflare. |
| Phone ntfy over the tailnet | **Yes** if it targets a LAN IP; no if it targets CT 101's tailnet address. |

So the operator can run G3 from an off-LAN Tailscale session and will lose LAN-IP reachability for
about ten seconds — but the SSH session to CT 250 itself, and CT 250's own SSH to CT 101, both
survive. **Prefer running G3 from CT 250 anyway**, since that path is pure LAN.

### 5.4 What G unblocks, and the gate it must not be read as passing

G removes the blocker on Step 4-A (kernel mode on CT 101). It does **not** authorize it. §8
CRITICAL-2 stands: any CT 101 restart goes through the Ansible `reboot` module, in a declared
window, with `ct:101` HA state confirmed `started` (it is: `pve1, started`, `failback 1`,
`max_relocate 1`, `max_restart 3`) and replication current (it is: `101-0`→pve2 and `101-1`→pve3,
both OK at 15:15, `*/15` schedule). `pct reboot 101` remains forbidden.

| Risk | Likelihood | Mitigation |
|---|---|---|
| `tailscale set --accept-routes=false` also silently clears `AdvertiseRoutes` | Very low — both flags are passed together in the compose path, and G1 passes only `--accept-routes` | G1 and G5 both assert `AdvertiseRoutes` and `PrimaryRoutes` explicitly; G6 re-arms in one command |
